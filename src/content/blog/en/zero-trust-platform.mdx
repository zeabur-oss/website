When you click “Delete service” on a platform, how does it delete the Deployment in Kubernetes for you?

The most straightforward approach is to give the platform a <Term word="ServiceAccount">A Kubernetes account for software. A program uses the account's token to call the Kubernetes API. The cluster's RBAC configuration determines what it can do.</Term> with access to the cluster. The platform checks whether you're allowed to delete the service, then calls the Kubernetes API with its own ServiceAccount. If that account has access to every <Term word="Namespace">A space that separates resources in Kubernetes, such as `dev` or `production`. Permissions can be limited to a single Namespace.</Term>, the platform's own permission checks are the only thing limiting what each user can do.

Zeabur Open Source leaves that decision to Kubernetes. Once a user signs in, it calls the same API with that user's token. Suppose the user can only delete Deployments in the `dev` Namespace. If they try to delete a Deployment in `production` through Zeabur Open Source, <Term word="kube-apiserver">The Kubernetes API server. Requests to read or write cluster resources go through it, whether they come from `kubectl` or another program. It verifies identity and checks permissions.</Term> rejects the request under <Term word="RBAC">Role-Based Access Control. Kubernetes uses Role and ClusterRole objects to define which operations are allowed on which resources, then assigns those roles to users or groups through RoleBinding and ClusterRoleBinding objects.</Term>[^user-client].

## Why does a platform breach affect its customers?

Several developer platforms were breached in October 2026 alone. According to Wiz, at least nine AI developer platforms disclosed security incidents that month. Attackers were after much the same thing: environment variables stored by the platforms, especially API keys for AI services[^wiz-black-october].

Zeabur was one of them. An attacker obtained a cluster admin token with no expiration, reached the platform database, and exfiltrated data for 321,810 accounts and 3,218,965 environment variable records[^zeabur-october]. A week later, an attacker at Railway escalated privileges from the build infrastructure, obtained CI credentials, and decrypted some of the environment variables stored in encrypted form. Up to about 100,000 workspaces were affected[^railway]. By the end of the month, secrets stored in Northflank's control plane had also been decrypted. Customers reported unauthorized use of their AI API keys, and Northflank had to ask all customers to assume every environment variable was compromised and rotate them all[^northflank].

This had happened before. In Zeabur's August incident, the attacker entered through a vulnerability in a user container and eventually reached the production database, obtaining the names and values of project environment variables[^zeabur-august]. Vercel's entry point was a third-party AI tool used by an employee[^vercel]. CircleCI's was malware on an engineer's laptop[^circleci]. GitHub integrations were compromised through stolen OAuth tokens held by Heroku and Travis CI[^github]. After Codecov's uploader was tampered with, it sent environment variables straight out of customers' CI environments[^codecov].

The entry points differed, but the attackers wanted the same things. **Platforms store customer data and hold the credentials needed to access customer resources**. Often, another key inside the platform is all that protects that data: Zeabur's cluster admin token, for example, or Railway's CI credentials. Encryption doesn't stop the attacker when the platform also holds the decryption keys. Railway's and Northflank's environment variables were decrypted; CircleCI's encryption keys were extracted directly from a running process.

**Once attackers breach the platform, they can use its identity to read every customer's data**. A compromised platform means compromised customers.

## Users shouldn't have to trust the platform

NIST SP 800-207 describes Zero Trust as refusing to grant implicit trust just because a request comes from an internal network or a company-owned device. Access still requires authentication and authorization, with only the permissions needed for the operation[^nist].

Apply that principle to the platform itself: **users shouldn't have to trust the platform**. Instead of holding a credential that can act on every customer's resources, the platform acts on each user's behalf with that user's permissions. The system hosting the resource decides whether to allow each request based on the user's identity.

That way, **even an attacker who breaches the platform has no master key**. The only tokens available belong to people currently using the platform. Each token expires, and none grants more access than its user already has. CircleCI's advice after its incident follows the same idea: use <Term word="OIDC">OpenID Connect, a sign-in standard built on OAuth 2.0. The party that verifies identities and issues tokens is called the issuer. It publishes public keys for signature verification, so a service receiving a token can check who issued it and whom it was issued to. OIDC tokens for CI are issued by the CI platform and expire quickly. Cloud services verify the signature before granting access, so the CI environment doesn't need to store long-lived keys.</Term> tokens and store fewer long-lived credentials[^circleci].

Back to deleting a Deployment: Zeabur Open Source uses the user's token directly, so it doesn't need to keep a shared credential with access to every Namespace. The same RBAC rules apply whether you use Zeabur Open Source or run kubectl yourself.

That's the theory. How does it work in Kubernetes?

## How does Kubernetes know whose token it is?

Suppose Alice has signed in and received a signed <Term word="JWT">JSON Web Token, a common token format. It contains a JSON payload with information such as a username, groups, and expiration time, along with the issuer's signature.</Term>. The token contains her username and groups. How does kube-apiserver know it's really Alice, rather than someone sending a token they made up?

Kubernetes already supports OIDC authentication[^authentication]. A cluster administrator configures a trusted issuer: the authentication server that issues tokens. kube-apiserver verifies signatures with that issuer's public key, then maps the token's claims to Kubernetes users and groups. An expired token, or one that wasn't signed by a trusted issuer, fails authentication.

RBAC comes next. If Alice belongs to the `dev` group and an administrator grants that group access to the `dev` Namespace, Alice can work with resources there. RBAC permissions are additive, with no deny rules. If another binding grants Alice broader permissions, she gets those too[^rbac].

Zeabur Open Source only needs to include Alice's token in the request. It doesn't need its own list of the Namespaces she can access.

### Connecting Zeabur Identity users to RBAC

Zeabur Identity is the OIDC issuer for Zeabur Open Source and primarily uses <Term word="passkeys">Sign in with a fingerprint, face recognition, or the screen lock on your phone or computer, without a password. The private key stays on the device; the website stores only the public key. A passkey is also bound to the website's domain, so a fake site can't obtain a usable sign-in credential.</Term> for sign-in. It keeps track of users and groups. The cluster administrator configures which Kubernetes resources each group can access[^users].

`zeabur-identityctl kube-config` generates an `AuthenticationConfiguration` for kube-apiserver. For example, `alice` in Zeabur Identity maps to `zeabur:alice` in Kubernetes, and the `dev` group becomes `zeabur:dev`. The `zeabur:` prefix keeps these mapped identities separate from built-in identities that start with `system:`[^identity-config].

To let the `dev` group edit resources in the `dev` Namespace, create this RoleBinding. Zeabur Identity's documentation also recommends binding roles to groups rather than individual users[^users]:

```sh
kubectl create rolebinding dev-edit --clusterrole=edit --group=zeabur:dev -n dev
```

When Alice signs in with `dev` in her token's groups, kube-apiserver grants her the permissions from this binding. Zeabur Identity's own ServiceAccount can't create RBAC objects and has no `impersonate` permission. It can read only a few Secrets of its own, and each must be requested by name. The default admin binding is applied by the cluster administrator, using their own permissions, during installation[^identity-rbac].

## Who issues the key card? Who opens the door?

If issuers, signature verification, and RBAC still feel abstract, think of a hotel key card.

Zeabur Identity is the front desk. Signing in with a passkey is like showing your ID at check-in. The front desk gives you a key card marked “Alice, dev team.” kube-apiserver is the door lock: it checks that the front desk issued the card, then looks up which rooms the dev team can enter (RBAC). Zeabur Open Source is a runner who carries your card and uses it to open doors for you. The runner has no separate key that opens every room.

How long does that card last? If it never expires, the platform can keep acting on your behalf once it has it. Zeabur Identity's regular access tokens expire after 10 minutes by default; admin tokens expire after 5 minutes. Within a session, a refresh token can get you a new card, so you don't have to use your passkey every 10 minutes. By default, though, a session ends after 1 hour of inactivity. Even with refreshes, it lasts no more than 12 hours from sign-in by default[^admin-sessions].

Structured Authentication Configuration, stable since Kubernetes v1.34, can use <Term word="CEL">Common Expression Language, an expression language designed by Google. Kubernetes uses it to write conditions in configuration, such as checking a claim's value in a token. It can evaluate expressions but can't execute arbitrary programs.</Term> to check token claims[^kep-3331]. The configuration generated by Zeabur Identity has kube-apiserver check token lifetimes: tokens whose `exp - iat` exceeds the limit are rejected[^identity-config].

> Access tokens use the JWT format defined in RFC 9068 and must contain a `client_id` claim[^rfc9068]. The kube-apiserver configuration generated by Zeabur Identity checks this claim to reject ID tokens[^identity-config].

If someone steals a token from the platform, they can use it to access resources Alice has permission to use until it expires. A stolen admin token gives them more access. That's why Zeabur Identity admin accounts can sign in only with passkeys. Their tokens carry the `zeabur:admins` group, which is bound to `cluster-admin` during installation[^identity-rbac]. The recommendation is to use a separate regular account for everyday work and sign in with the admin account only when you need to administer the cluster[^admin-sessions].

The issuer's signing keys also need protection. kube-apiserver grants access based on identities signed by Zeabur Identity. Anyone who can issue a forged “this is Alice” token can obtain Alice's permissions.

Incidentally, Zeabur Identity runs as a small Pod, uses less than 30 MiB of memory after sign-in, and has no database of its own. Users, credentials, and sessions are all stored as Kubernetes custom resources[^identity-architecture].

## How does the platform become an OAuth client?

Zeabur Open Source is an OAuth client of Zeabur Identity[^rfc6749]. It signs users in with the authorization code flow and <Term word="PKCE">Proof Key for Code Exchange. At the start of sign-in, the client sends a hash of a random value. Later, when exchanging the authorization code for a token, it must present the original value. Even if someone intercepts the code, they can't exchange it for a token without that value.</Term>[^rfc7636], with security settings based on RFC 9700[^rfc9700][^auth-client]. First, register it as a <Term word="confidential client">An OAuth client that can securely store a client secret, usually a server-side program. It must present the secret when exchanging a code for tokens. A public client, such as a browser-based single-page app or a mobile app, runs code in the user's hands and can't keep a secret.</Term>[^installation]:

```sh
zeabur-identityctl client create zeabur \
  --type confidential \
  --audience kubernetes \
  --display-name Zeabur \
  --redirect-uri https://zeabur.example.com/auth/callback \
  --home-url https://zeabur.example.com/ \
  | kubectl apply -f -
```

The sign-in flow looks roughly like this:

<PostFigure
  name="login-flow"
  label="Four lanes (the browser, Zeabur Open Source, Zeabur Identity and kube-apiserver): passkey sign-in, a code exchange with PKCE for tokens, then the user's token on every request, with a refresh as it nears expiration"
/>

The dashed lines are round trips that happen only during sign-in. After that, only the bottom two solid lines remain: Zeabur Open Source sends your token directly to kube-apiserver with every request.

When Zeabur Open Source needs to know who you are, for example to read account details, it uses `SelfSubjectReview` to ask kube-apiserver “who does this token belong to?” It doesn't determine the user's identity by interpreting an ID token itself[^auth-client][^adapter].

The `zeabur-kube` crate makes the Kubernetes API calls. It creates clients with the user's token. The sole exception is the terminal, which uses Zeabur Open Source's own ServiceAccount[^user-client]. That ServiceAccount is bound to a single Role that lets it create Pods in a dedicated terminal Namespace and connect to them to run commands[^terminal-rbac]. For example, this command checks whether it has permission to impersonate other users:

```sh
kubectl auth can-i impersonate users --as=system:serviceaccount:zeabur:zeabur
```

This command checks `impersonate users`. To check permissions on other resources, substitute the corresponding operation. The result also changes if the cluster administrator binds additional roles to this ServiceAccount.

Secrets are read with the user's token too. The list shows only names, types, and key counts; values are fetched from Kubernetes only when you ask to reveal them[^ui-copy]. Whether you can see a Secret's contents therefore depends on your permission to read it[^adapter][^objects].

What happens when you don't have enough permission? Zeabur Open Source doesn't retry with its own identity. When kube-apiserver rejects a request, the interface lists the missing permissions and the original Kubernetes response, and asks you to contact an administrator[^refused]. On the cluster page, you can also copy the required ClusterRole to send to the administrator[^forbidden].

![A regular account lacks permission to view nodes. Expanded details show the missing list nodes permission, HTTP status 403, and the Kubernetes response, with an option to copy a ClusterRole below](/blog/zero-trust-platform/en/refused.avif)

If you need to administer the cluster yourself, sign out and sign back in with your admin account using a passkey. The RBAC permissions associated with that token still determine which operations succeed[^admin-sessions].

![The Zeabur Identity sign-in page for continuing to Zeabur, with Sign in with a passkey as the primary button](/blog/zero-trust-platform/en/sign-in.avif)

Zeabur Open Source keeps no separate copy of project data. A project is a Kubernetes Namespace. If you remove Zeabur Open Source, your workloads stay in place, and you can keep managing them with kubectl, Helm, or your existing GitOps tools[^uninstall]. To revoke a user's access, change the corresponding RBAC bindings.
